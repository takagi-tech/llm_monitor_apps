## 1. これは何のためのツール？

研究室にある **複数のGPUマシン** のうち、

- 今 **どのマシンがオンラインか**
- そのマシンに **どのモデルが載っているか（vLLM / sglang / llama.cpp 等）**

を、SSHで1台ずつ確認しなくても **ブラウザで一覧把握** するための、軽量な稼働モニターです。

GPUマシンはモデルの載せ替えが頻繁なので、「今の状況」を全員が同じ画面で見られることを目的にしています。

---

## 2. ネットワーク構成

研究室のネットワークは **2つ** あり、性質がまったく違います。ここがこのツールの運用の肝です。

| ネットワーク | IPレンジ | インターネット | 用途・性質 |
|---|---|---|---|
| **AI2** | `192.168.86.x` | **接続可** | 通常のローカルネット。外部からパッケージ取得なども可能 |
| **AI3** | `10.0.1.x` | **非接続（閉域）** | **実際の医療データを扱う閉域ネット。エアギャップ厳守** |

### ⚠️ 最重要ルール：AI2とAI3をつなげない

- **AI3に接続する機器を、AI2やインターネットに同時接続してはいけません。**
- 理由：AI3には医療データがあります。両方につながった機器が1台でもあると、
  そこが「インターネット ↔ 医療データ閉域」の橋になり、情報漏洩の経路になり得ます。
- したがって、**1台のマシンで両ネットをまとめて監視する構成（デュアルホーム）は採用しません。**

---

## 3. デプロイ構成：ネットごとに1台ずつ

上のルールから、**監視アプリはネットごとに独立して1インスタンスずつ** 動かします。

```
┌─ AI2（192.168.86 / ネット可）──────┐   ┌─ AI3（10.0.1 / 閉域・医療データ）──┐
│  監視用マシン(例: Raspberry Pi)    │   │  監視用マシン(例: Raspberry Pi)     │
│  でアプリを常時起動                │   │  でアプリを常時起動                 │
│  → AI2のGPUマシンだけ監視          │   │  → AI3のGPUマシンだけ監視           │
│  → endpoints.json は AI2分のみ     │   │  → endpoints.json は AI3分のみ      │
└────────────────────────────────────┘   └─────────────────────────────────────┘
     PCをAI2に繋いでURLを開く              PCをAI3に繋いでURLを開く
              ※ 2つのネット・2つのインスタンスは完全独立。橋渡しなし
```

### 監視マシンの想定：Raspberry Pi（常時起動の専用機）

- **構想中**：各ネットに Raspberry Pi を1台ずつ置き、Dockerでアプリを常時起動する。
- 利点：高価なGPUマシンを監視のために占有しない／消費電力が小さく付けっぱなしにできる。
- `docker-compose.yml` に `restart: unless-stopped` を設定済みのため、Pi再起動後も自動で立ち上がります。

### 使う側（研究室メンバー）の動線

1. 見たいネットワークに自分のPCを接続する（AI2 か AI3）。**両方同時には繋がない。**
2. そのネットにある監視Piのアドレス（例：`http://<PiのIP>:8000/`）をブラウザで開く。
3. 一覧で各GPUマシンの状態・モデル名を確認する。

## 4. デプロイ手順（AI2 と AI3 でやり方が違う）

### 4-1. AI2（ネット接続可）— 普通にビルドしてOK

AI2はインターネットに出られるので、Pi上で直接ビルドできます。

```bash
# AI2のPi上で
git clone <リポジトリ>        # or ソースを配置
cd llm_monitor_apps
docker compose up --build -d
```

- 起動後、ブラウザで `http://<PiのIP>:8000/` を開く。
- `endpoints.json` には **AI2のGPUマシンだけ** を登録する。

### 4-2. AI3（閉域）— ビルドせず「持ち込む」

AI3はインターネットに出られないので、**Pi上で `--build` は失敗します**
（`python:3.12-slim` の取得・PyPIからのDLができないため）。

そこで「ネットの使えるところでイメージを作り、ファイルにして物理的に持ち込む」方式を取ります（スニーカーネット）。

```bash
# 【ステップ1】ネットの使えるARM機（例：AI2のPi）でイメージをビルド
docker compose build

# 【ステップ2】イメージをtarファイルに書き出す
docker save llm-monitor-apps-web:latest -o llm-monitor.tar
#   ※ イメージ名は `docker images` で確認して読み替える

# 【ステップ3】USBメモリ等で llm-monitor.tar を AI3 のPiへ物理的に運ぶ

# 【ステップ4】AI3のPiで読み込んで起動（--build は付けない）
docker load -i llm-monitor.tar
docker compose up -d
```

- `endpoints.json` には **AI3のGPUマシンだけ** を登録する。

#### ⚠️ AI3デプロイの注意点

1. **CPUアーキテクチャを一致させること。**
   Raspberry Pi は **arm64（ARM）**。x86のPCで作ったイメージはPiで動きません（`exec format error`）。
   → **Piと同じARM機（AI2のPi等）でビルドする**のが確実。
   （Apple SiliconのMacで作った場合も arm64 になるので一致します）

2. **USBの運用ルール。**
   USBは閉域にマルウェアが入る古典的な経路です。
   AI3に挿すUSBは **専用のものを決め、他で使い回さない** ことを推奨します。

## 5. 使い方（画面操作）

1. トップページを開く。
2. `名前` `ネットワーク` `IPアドレス` `ポート` を入力してGPUマシンを追加する。
   - 登録直後に、自動でモデル名の取得を試みます。
3. 一覧では、AI2 / AI3 のネットワークごとにグループ分けして表示されます。
4. 各行の操作：
   - **Ping**：`/health` を叩いてオンライン/オフラインを更新
   - **削除**：登録を削除
5. 一括操作：**全台Ping**（`ping-all`）で登録済みマシンをまとめて疎通確認できます。

> モデル名は `/v1/models` → `/props` の順で取得します。
> モデルが立っていない場合は「現在、モデルは立っていません」と表示されます。

---

## 6. データについて

- 登録データは各Piの `endpoints.json`（JSONファイル）に保存されます。DBは使っていません。
- `docker-compose.yml` でホスト側の `endpoints.json` をバインドマウントしているので、
  コンテナを作り直しても登録内容は残ります。
- **AI2用とAI3用で `endpoints.json` の中身は別々**（各ネットのマシンだけ）になります。
